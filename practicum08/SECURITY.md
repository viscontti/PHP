# Аудит безпеки — практична робота №8

Варіант 13, «Трекер особистих витрат». Аудит охопив практикуми №1–7. Практикум №8 — фінальний застосунок після виправлень.

## Як запустити

```sh
docker exec -i php-mysql mysql -uroot -proot --default-character-set=utf8mb4 < sql/schema.sql
php -S localhost:8008 router.php
```

Тестові користувачі: `veronika` / `veronika2026`, `olena` / `olena2026`.

Перевірки:

- `sh tests/security_check.sh` — 41 перевірка через curl;
- `php tests/csrf_test.php` — граничні випадки CSRF-токена.

Демонстрація CSRF-атаки: `php -S localhost:9008 -t attack`, потім відкрити
`http://localhost:9008/csrf_attack.html?target=http://localhost:8008/add.php`.

## Чому CSRF-перевірка відхиляє запит, коли токена в сесії немає

`hash_equals('', '')` повертає `true`.
Якщо порівнювати `$_SESSION['csrf_token'] ?? ''` з `$_POST['csrf_token'] ?? ''`, то для сесії без токена й запиту без токена перевірка проходить.
Тому `isValidCsrf()` у `bootstrap.php` спершу окремо перевіряє, що обидва токени — непорожні рядки, і лише потім викликає `hash_equals()`:

```php
$sessionToken = $_SESSION['csrf_token'] ?? null;
$sentToken = $_POST['csrf_token'] ?? $_SERVER['HTTP_X_CSRF_TOKEN'] ?? null;

if (!is_string($sessionToken) || $sessionToken === '') {
    return false;
}
if (!is_string($sentToken) || $sentToken === '') {
    return false;
}
return hash_equals($sessionToken, $sentToken);
```

Токен генерується в сесії, коли сторінка вперше видає форму, і заново після входу й виходу.
Через це токен із попередньої сесії більше не діє.
Додаткові заходи:

- cookie сесії має прапорці `HttpOnly` і `SameSite=Lax`;
- після входу викликається `session_regenerate_id(true)`.

Підтвердження `confirm()` захищає лише від випадкового кліку.
Від підробленого запиту захищають тільки POST і CSRF-токен.
